# ShopFlow architecture and operations

One Express/TypeScript application serves authenticated JSON APIs, device ingestion, SSE and the built React application. Vite proxies `/api` during development. Prisma uses MySQL 8/InnoDB. No Redis, MQTT or microservices are required.

## Event and processing contract

`POST /api/v1/events` accepts one JSON envelope per request (16 KB maximum). Supply `Authorization: Bearer <token>`. `schemaVersion` is currently `1`; supported types are `sensor.state_changed` with `{detected:boolean}` and `cycle.completed` with `{durationMs:integer}` from 1 ms through 24 hours. Required fields: UUID `deviceId`, unique `eventId` (1–100 characters), `bootId` (1–100 characters), nonnegative `sequence` (32-bit signed range), nonnegative safe-integer `uptimeMs`, and UTC ISO `occurredAt` or null. Sequence is shared by all production types; heartbeats do not consume it. Unknown fields/types/versions are rejected, not coerced.

Optional `delivery` is `live`, `buffered` or `unknown` (default). Device timestamps are recorded as `device_clock`; future timestamps beyond five minutes are rejected. They are claims from a device, not proof of synchronized time. When the timestamp is null, only explicit `delivery:live` permits a labeled `receipt_estimate`. Otherwise time quality is `unknown` and derived output remains unplaced. Unknown timestamps are excluded from shift totals; quality notices and the all-time unplaced-parts count prevent silent loss from the operator's view. Raw events preserve both timestamps and time quality.

The transaction derives organization/device from the hashed token, locks the device row with `FOR UPDATE`, rechecks credential revocation/status, verifies the submitted device ID and capability, checks the `(deviceId,eventId)` unique key, snapshots workstation/product/job/count interval, writes the raw event, updates durable state, writes derived measurements, and commits. Only then does the route acknowledge `{ok:true,duplicate:false}` and publish an SSE refresh. Retries return 200 with `duplicate:true`; the first committed payload wins if an event ID is reused with different content. Raw-event APIs are read-only. There is no raw update/delete route.

`POST /api/v1/heartbeat` accepts `{deviceId, firmware?}` and the same credential. Heartbeats update connectivity only; they never create production events or advance production sequence state. Online means a heartbeat within 90 seconds; no heartbeat means never connected, even if a production event has arrived. Offline is a freshness warning, not zero output.

For each device/rule version, persistent boot state tracks sequence, last state, uptime, and last accepted count uptime. A first state is a baseline. Only false → true counts; rejected debounce edges still consume the high state. A sequence gap resets the baseline. Older sequences, decreasing uptime and events from a previously superseded boot are retained but excluded. A new unseen boot becomes active. This conservative arrival-order rule can undercount buffered interleaved boots; the system does not reconstruct missing production. Retain monotonically increasing sequence within a random boot ID.

`npm run rebuild` walks immutable events in ingestion ID order with 200-row transactions. It locks each device and commits measurements/checkpoints together. Reruns resume without duplicates. `processRaw` accepts a rule version for explicit, reviewed migrations; changing `RULE_VERSION` selects the dashboard version. Rebuild a new version before switching readers; do not delete/rewrite old raw events. Rebuild uses snapshotted interval/product/job/assignment, not current device configuration.

## Access and deployment

Passwords use bcrypt cost 12. User sessions are random 256-bit credentials with only SHA-256 hashes in MySQL; CSRF tokens and 8-hour expiration also live there. Cookies are HttpOnly, SameSite Strict and Secure in production. Cookie mutations require matching Origin and session CSRF header, including logout. Login is Origin-checked and limited to 20 attempts per 15 minutes/IP. API requests are limited to 600/minute/IP; shared NATs may need a reviewed adjustment. Bodies are capped and database transactions are bounded. HTTP header/request/socket timeouts are configured. Logs contain method, path, status and elapsed time, not credentials or bodies.

All protected routes derive orgId from the session. Viewers read dashboards/reports/floor display/export; supervisors additionally inspect raw events, edit workstation configuration, and add notes; admins manage device credentials, assignments, structure, shifts and users. SSE uses the authenticated organization channel and rechecks session/account every 15 seconds. It sends invalidation notifications; clients refetch authoritative state on notification/reconnect and poll every 30 seconds. Notes refresh in station detail every five seconds.

Deploy **one application instance** behind HTTPS. Set `APP_ORIGIN` to the exact public origin and `NODE_ENV=production`. Serve the built frontend and API on the same origin. The server binds to loopback by default; put the proxy on the same host. Disable SSE proxy buffering and allow streaming responses. Apply migrations with a deployment DB role, then use a restricted runtime role. Back up MySQL and verify restores. Expired sessions can be purged with a scheduled SQL maintenance job. Monitor disk growth, credential failures, event gaps, unplaced output and ingestion latency.

Before horizontal scaling, replace process-local SSE fanout and rate-limit state with shared mechanisms; continue database locking and idempotency. Do not simply add replicas. Establish connection budgets, limits on SSE connections, retention policy and observability appropriate to actual fleet size. Production SQL permissions should restrict RawEvent to SELECT/INSERT, not UPDATE/DELETE, preserving immutability beyond the HTTP interface.

## Metrics and known limits

- Recorded output sums confirmed transitions with occurrence/estimated time inside a shift. A group with no timestamped measurements is unavailable, not zero. An offline station can still show earlier recorded output with an explicit data-unavailable status.
- Expected output is current target × elapsed scheduled working time / full scheduled working time. Breaks are half-open offsets from shift start; overlaps/out-of-shift breaks are rejected. Overnight windows and timezone/DST elapsed time are supported. All shifts recur daily; holidays and weekday calendars are not implemented.
- Daily reports use local calendar-day boundaries and prorate each overlapping shift's target by scheduled working time within that day, including the previous day's overnight shift. Overlapping shift definitions are additive; configure them carefully to avoid duplicate scheduled targets.
- Current targets, shift schedules and organization timezone apply to historical comparisons. They are **not historical target revisions**. Do not interpret edited schedules as the original historical plan; export before changes if historical plan evidence is needed.
- Median and p90 use nearest-rank device-measured cycle durations, capped at the most recent 10,000 matching cycle rows. The UI labels when that cap is reached. They never use inter-part intervals. There is no OEE computation.
- Notes/reasons are operator-entered and time-stamped on creation; no downtime is inferred. Durations are declarations, not automatically reconciled availability.
- Reports compare shifts and exact product filters; jobs/product are snapshotted on events. Station labels are current. Equivalence must be checked by the team. CSV neutralizes formula prefixes and preserves unavailable values.
- Raw events paginate in 50-row pages by immutable ID. SQL aggregates output and hourly charts; indexed measurement queries avoid transferring raw history to the browser. Cycles, timeline and notes are bounded. No summary table is needed for the initial single-instance fleet; add transactional/replayable rollups after measuring actual query load.
- Structure supports creation; deletion is deliberately absent to preserve references. Account creation uses an initial password; no email invitation, password recovery or SSO is included. Archived devices disappear from the active registry but history remains.
- Credentials display once in the UI and are never persisted in plaintext. A lost creation response requires rotation. Seed demo credentials are revoked after generation. Seed creates a distinct demo organization; real deployments should provision a separate production organization/account instead of renaming demo data.
- The simulator tests real HTTP ingestion. Arduino polling/RAM buffering has documented loss limits; no lossless claim is made.
